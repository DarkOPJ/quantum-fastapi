# Database: SQLAlchemy 2.0 (async) & Alembic

## Engine & session setup

- Use an async driver — `asyncpg` for PostgreSQL — with SQLAlchemy 2.0's native async support (`create_async_engine`, `AsyncSession`). A sync driver blocking the event loop on every query is the single most common FastAPI performance mistake — with a sync driver, 100 concurrent requests queue up one query at a time instead of running concurrently.

```python
# db/session.py
engine = create_async_engine(settings.database_url, pool_size=10, max_overflow=5)
async_session_maker = async_sessionmaker(engine, expire_on_commit=False)

async def get_db_session() -> AsyncGenerator[AsyncSession, None]:
    async with async_session_maker() as session:
        yield session
```

- `expire_on_commit=False` avoids surprise lazy-load errors after commit when the session is about to be closed at request end — a common FastAPI+SQLAlchemy gotcha.
- Inject the session via `Depends(get_db_session)`, never as a module-level global — this is what keeps connection pooling correct under concurrent requests and keeps repositories testable.

## Models (SQLAlchemy 2.0 style)

Use SQLAlchemy 2.0's typed declarative style (`Mapped`/`mapped_column`), not the legacy `Column(...)` style:

```python
class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(unique=True, index=True)
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
```

## Repository pattern

```python
# repositories/user_repository.py
class UserRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def get_by_id(self, user_id: int) -> User | None:
        return await self.session.get(User, user_id)

    async def get_by_email(self, email: str) -> User | None:
        result = await self.session.execute(select(User).where(User.email == email))
        return result.scalar_one_or_none()

    async def create(self, user: User) -> User:
        self.session.add(user)
        await self.session.flush()  # get generated PK without committing
        return user
```

- Repositories `flush()` to make generated IDs available; **commit happens at the service or request-transaction boundary**, not inside the repository — this keeps multi-repository operations transactional (a service calling two repositories should commit once, not have each repository commit independently).
- Use `session.stream()`/`AsyncScalarResult` for large result sets you want to iterate without loading everything into memory at once.

## Alembic migrations (async-aware)

- `alembic init alembic`, then configure `alembic/env.py` to run migrations against the async engine (or a sync driver used only for migrations — a common, simpler pattern: migrations run synchronously even though the app runs async, since Alembic's own execution model is sync-first).
- Autogenerate migrations from model diffs (`alembic revision --autogenerate -m "..."`), but **always read the generated migration before applying it** — autogenerate misses some changes (e.g., some check constraints, most data migrations) and occasionally proposes destructive operations you didn't intend.
- Gate destructive migrations (drops, renames) behind an explicit review step in CI/CD for production databases — never auto-apply an unreviewed autogenerated migration against prod.

## Definition of done for this phase
- [ ] Async driver (`asyncpg` or equivalent) used throughout — no sync DB driver blocking the event loop.
- [ ] All DB access goes through repositories; commits happen at the service/transaction boundary, not inside repository methods.
- [ ] Models use SQLAlchemy 2.0's `Mapped`/`mapped_column` typed style.
- [ ] Alembic migrations are reviewed (not blindly auto-applied) before hitting production, especially anything destructive.
